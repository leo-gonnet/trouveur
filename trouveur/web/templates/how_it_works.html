How it works

Three things happen, on three different clocks. Ingest builds one corpus for everyone. Your profile is turned into search terms once, when you change it. A run then selects from the corpus with those terms and publishes the day's edition.

Ingest — one corpus, shared by everyone

Boards are swept by their own structure, never with a user's keywords, so a job you would have wanted but never thought to type still arrives. Every derived table is a pure, versioned function of the raw archive: bump the version and every row is recomputed from it, by the same worker that handles new postings. What can be recommended is bounded by age as well as by whether the posting is still open: only the last seven days are embedded, kept in the index and searched, so a vacancy that has gone cold leaves the index instead of competing in it.

Your profile — read once, when you change it

Your profile is not searched with directly. It is turned into a set of search terms, and that happens once per version of the profile: saving a field that changes what a good match is bumps the version, and the next run pays to build the terms again. Nothing else rebuilds them — not a new day, not a new edition, not a scan that found ten thousand postings. That is the whole reason this is drawn as its own stage.

The invented adverts are there because a vacancy is written like a vacancy and a profile is not; searching by meaning works better when both sides of the comparison have the same shape. They only ever reach the meaning search. Your background is summarised here, once, rather than sent with every batch of postings to be scored — which is why the scorer sees the summary and never the whole field.

A run — select from the corpus, score, publish

A run reads the stored search terms and never writes new ones. It filters the corpus in SQL, searches what is left twice over — once by meaning, once by word — and merges the two by rank rather than by score, since the two arms have no common scale. Only the top of that list is sent to be scored, and only the postings not already scored under this version of your profile: a posting is paid for once, ever.

A run starts when the nightly scan finishes, and once more whenever you save a profile change, add a key, or switch scoring back on. There is no button for it: with nothing new to score a run would fetch nothing, cost nothing and change no pixel, so a button could not say whether pressing it would do anything.


What a run publishes is an edition — one page per day, keyed on the day a posting became a recommendation for you rather than on the day it was posted. An edition is stored as it was read, not recalculated, so it is never rewritten: a posting that later closes keeps its place with a closed tag, and only one you dismiss leaves. The single exception is today's, which a profile change replaces — after asking you first, because the new profile will score the same postings differently. Everything older stands as published. A posting reaches you once per profile version, ever; only changing your profile can bring it back.

Two processes share the database and nothing else: the web app reads and enqueues, the runner sweeps, drains and matches. Either can be down without breaking the other.
